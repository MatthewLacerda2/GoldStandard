# Working a batch of issues

The user rarely has one issue. An idea becomes several, and more appear as coding
starts. This is how a set of them gets worked without the batch costing more than
the work.

## How many agents at once

- **At most five agents write code at once**, cloud and local together. More
  buy conflicts and rebases, and the queue drains them no faster.
- `independent-review` reviewers do not count, and neither do agents that only
  read and think — research, review, planning: no worktree, no limit.
- A coder answering its review's findings is writing code, and counts. Review
  rounds stack on top of new work, so start the next coder only once the
  answering ones are back under the five.
- The orchestrator is one more, always.

Inside the five, file collision is the finer limit.

## The merge queue does the waiting; collision is the limit

Merging by hand costs the waiting, not the runner: whoever merges watches CI,
rebases, waits again, merges and deletes the branch, holding their whole context
open the entire time, once per pull request. A fast CI does not make that free,
and a project made from this template will have a slower one. So the batch's
session never sits through CI: it reads the diff, labels the pull request
`queue` once it is reviewed and ready, and keeps one watch running in the
background for the whole batch (`ci-merge`, *Feeding the merge queue*). The
queue hands back only what needs somebody.

What the queue cannot drain is the collision between branches. Over shared
files, N branches cost **N(N−1)/2 rebases**. That is git's bill, not the
runner's: the queue does a clean rebase in seconds, but hands a colliding one
back, and that one is a session. **Cap the number of branches in flight on file
collision**, not on CI, and not on a person's reading time, because nobody reads
the diffs (`CLAUDE.md`, *Pull Requests*).

## Merges serialize per layer, not globally

CI runs a layer's gates only when the branch touches that layer (`ci-merge`,
*CI as it runs today*, has the paths). Two branches in different layers do not
share a gate and cannot break each other's, so they merge in either order, or at
once, and a re-run buys nothing.

**Within one layer they do serialize**, for a narrower version of the reason a
compiled repo serializes everything:

- `bun run check` runs `tsc --noEmit` over the whole frontend. One branch changes
  an exported type, another adds a caller; each is green alone and red together.
- `pytest` imports the whole backend. A helper removed here and used there is the
  same failure in a different language.

The queue does not re-verify a branch that merges cleanly: it merges it as it
is, and `main`'s own run of the merge is what catches the pair. A red `main`
then holds every other merge until the fix lands (`ci-merge`, *Feeding the
merge queue*), so the damage is one fix branch, not a broken batch. When two
branches in one layer touch the same shared surface (an exported type, a
helper), skip even that: **label the second only once it is rebased onto the
`main` the first landed in**, so its own run re-verifies the pair. Across
layers, do not bother.

The exception cuts the other way, and it is the dangerous one. **The contract
*between* the layers is checked only in part.** `make front-contract` holds the
answer each frontend request reads to the endpoint it hits, by field name and
kind (list, object, scalar); a scalar's type, nullability and request bodies
are still a human promise. Two branches that
split one API change between them can both be green and the app broken. Keep an
API change on one branch.

## The files where everything collides

The ones every feature appends to. Two branches landing in the same one at the
same time is the case to avoid:

- **The `Makefile`, root `CLAUDE.md`, `README.md`, `.github/workflows/ci.yml`
  and `tools/ci_paths.py`** — every new gate or tool is a target, a line in the
  gate list, a practices bullet and often a path. Infrastructure branches
  collide here more than features collide anywhere: each merge sends the other
  open ones back to rebase. Run infrastructure branches that add a target one
  or two at a time.
- **`frontend/src/routeTree.gen.ts`** — generated by the TanStack Router plugin,
  rewritten by every new route. Its merge driver regenerates it from both sides'
  routes, once the clone ran `make setup`; without it, **regenerate, never
  hand-merge**.
- **`frontend/src/i18n/locales/{en,pt,es}.json`** and **`frontend/openapi.json`**
  — every user-facing string lands in three files, every API change in the
  contract. Their merge driver settles them key by key after `make setup`; a
  key both sides changed still conflicts.
- **`frontend/src/styles.css`** — the `@theme inline` block *is* the design
  system's allowlist. Every new token appends here.
- **`frontend/eslint.config.ts`** and **`frontend/eslint-rules/index.ts`** — every
  new house rule is a line in each.
- **`frontend/bun.lock`** — never hand-merge it. Take one side whole and re-run
  `bun install`.
- **`backend/api/endpoints.py`** — every new router is a line here, and whether it
  goes above or below the `get_current_user` dependency is a decision, not a merge
  accident.
- **`backend/models/__init__.py`** — every new model, twice: the import and
  `__all__`.
- **`backend/core/config.py` and `.env.example`** — every new setting, in both,
  and a merge that keeps one and drops the other fails at startup, not at lint.
- **`backend/tests/api/conftest.py`** — every shared fixture.
- **`backend/requirements.txt`** — trivial to resolve, but a conflict all the same.

**Before starting a second branch, ask whether it lands in any of these.** Three
branches in `repositories/`, `components/ui/` and a workflow file barely touch each
other. Two branches both adding a route, or both adding copy, collide by
construction.

**Migrations are not a serializer today, and will be.** `init_db()` is additive
`create_all` with no Alembic, so two branches each adding a table or a column
merge in any order. That is a property of this skeleton, stated as a deliberate
upgrade path in `README.md` — not of the stack. The day a downstream repo adds
Alembic, two branches each generating a revision collide on `down_revision`, and
this section is wrong until it is rewritten.

## Group the work before splitting it

**Split by responsibility, not by parallelism.** If a parent's sub-issues all land
in the same file, they are **one branch**, not one each.

Splitting an issue so several agents can run at once optimises the half that was
never scarce, and manufactures collisions: four sub-issues each adding a locale key
is four rebases and four reviews for one coherent change. Sub-issues are for work
that is genuinely separable *in the code*, not for work that is merely listable.

A small change need not be a branch. It may ride along in whichever pull request
is already standing in that file.

## One worktree per branch

`CLAUDE.md` already mandates it. The reason is in `backend/tests/conftest.py`: the
test database is named `test_gs_<sha1 of the worktree root>`, so every worktree
gets its own database against the one shared postgres, automatically.

Two branches taking turns in one checkout share that database — and because
`create_all` **adds and never drops**, its schema becomes the union of everything
either branch ever declared. A column one branch removed sits there, and the other
branch's next insert fails on a `NOT NULL` nobody wrote. Cheap to avoid,
expensive to diagnose.

Three things a worktree does *not* isolate:

- **The compose stack is a singleton.** It binds 5432, 8000 and 3000 on the host,
  so only one worktree can hold it. `CLAUDE.md` says not to start it to "check"
  something anyway — the gates are how you verify.
- **Anything under `~`.** Bun's and pip's caches are shared, which is fine, and is
  the reason parallel gate runs are cheap here.
- **The repository config.** Every worktree reads the same `.git/config`, so a
  `git config` run in one (`make setup`'s hook path and merge drivers included) changes it
  for all of them and for the main checkout.

A worktree costs `backend/.venv` and `frontend/node_modules` — hundreds of
megabytes, not the gigabytes a compiled target directory costs — so removing one is
hygiene rather than survival. **Remove it the moment its branch merges** anyway: a
stale worktree keeps a stale test database alive behind it.

## Starting

- Assign the user the moment work actually begins, and tell them. No assignee
  means free for grabs. **Unassign** if it turns out the issue was never started.
- Worktree off the latest `main`, branch `feat/…` or `fix/…`, pushed under the
  same name. Install the layers it will touch there (`make back-install`,
  `make front-install`): the pre-commit hook refuses a commit to a layer whose
  tools are missing. The hook itself is `make setup`, once per clone, never per
  worktree.
- The pull request says `Closes #N` for the issue it closes — with the number
  checked — and is opened as a **draft** on the first push (`ci-merge`, *What a
  ready pull request claims*).

## The path to merged

Each branch takes the `ci-merge` path, the same as outside a batch. What the
batch changes:

- **Starting the batch was the approval**, so each pull request merges the
  moment `ci-merge` clears it, without asking.
- **The batch's session reviews and labels; the queue merges; the coder does
  neither.** The session dispatches `independent-review` when a trigger hits,
  sends the findings back to the coder to answer, and labels the pull request
  `queue` once it is ready. A hand-back goes to the coder that wrote the branch.

## Re-read the board after every merge

A merge changes the graph. Whatever the merged issue blocked is fair game the
moment it lands — so the decision is one merge wide, not one batch wide.

Re-reading is not a licence to start everything. The ceiling is five coders and the
collision list above, and an unblocked issue left unstarted is not wasted
capacity — it is a rebase not yet paid for. Priority (`infrastructure` →
`architecture` → `fix` → `foundation` → `feat`, `documentation` any time)
orders what gets **merged**, not what gets started.

**A stage label is the only absolute stop.** `planning` and `human` mean *not
yet*, and no amount of the issue looking ready overrides that. Everything else is
startable the moment it exists, including an issue filed a minute ago.

## Briefing a subagent

Point it at the root `CLAUDE.md`, then the layer contract it will live in —
`backend/CLAUDE.md` or `frontend/CLAUDE.md` — then the issue, which is written
to be read cold (`CLAUDE.md`, *Issues*). Beyond that:

- Name the **base commit** and what has landed recently that it must respect,
  and have it `git fetch origin` right before it reports that `origin/main` has
  not moved: in a busy batch, it has.
- Name the **siblings** and which files they are touching.
- Start it with a **description that names its issue** (`#<n> <what it does>`):
  `make claude-usage` ties an agent's tokens to a pull request by that number.
- Tell it which gate to run — the layer target while working, `make check` before
  the pull request goes ready — and point it at `ci-merge` for the rest.
- Tell it **not** to merge or label `queue` — merging belongs to the queue the
  batch's session feeds.
- Tell it **not** to review its own pull request. When a trigger hits, the
  batch's session runs `independent-review` and sends the findings back to the
  coder (`SendMessage` resumes it with its context) to answer.
- Tell it **not** to start `docker compose`, a dev server, or anything
  long-running. The stack is a singleton and the gates are the verification.
- **Scratch filenames must carry the issue number.** The scratchpad is shared
  between sibling agents, and a collision swaps one pull request's description for
  another's.

## When to hand back to the user

- ≈3 attempts at the same failure.
- **A decision that is genuinely theirs.** This repo's reader is a developer, so
  hand back the engineering call rather than a simplified version of it — name the
  options and what each costs. The ones that are always theirs: a change to a
  request or response shape, a route or token name people will type, a layer
  boundary, what a lint rule allows, and anything that moves what the
  **template teaches** — an upgrade path taken early, a convention the
  downstream reader will inherit — or changes stored data, how the user sees
  their existing data, or needs a migration (`CLAUDE.md`, *Issues*). A check
  for a convention already written down is not on this list.
- The mechanics, per `CLAUDE.md`: push what you have, leave the pull request
  **draft**, comment the bottleneck, tag the user, and stop. Do not thrash.

Working unattended, a question that only blocks *one* issue is a comment on that
issue and a move to the next — not a night spent idling. A question that blocks the
batch is a hand-back.

**Everything else is decided, written down, and not waited on.** A judgement call
the issue left open — and that is not on the list above — takes the default the
issue, `CLAUDE.md` or the worked `items` example points to; the pull request says
what was chosen and why. **A human check is never a hold either.** Some proof only
a person can give: the page in a real browser, how it looks, a flow clicked
through. Agents do not start the app (`CLAUDE.md`, *Server-start guardrails*), so
put the check in the pull request as a `- [ ]` checklist under `## For a human`
for the user to run later, and carry on. If it turns out broken, that is a bug to
file and fix, not a reason the batch waited.

## Learn from the batch: every lesson ends as a change

A batch is trial by fire: it finds the traps, gaps and bugs in the tooling and in
the template faster than anything else. A lesson that only reaches the chat is
lost, because the next session starts without it, and one kept in Claude's local
memory reaches only this developer's sessions (`CLAUDE.md`, *Memory is the
developer's*). So every lesson ends as exactly one of:

- **fixed** — a pull request that removes the cause;
- **enforced** — a lint rule, gate or test that makes it impossible to repeat,
  the first choice whenever a machine can tell (`CLAUDE.md`, *A convention a
  machine can check is a gate*);
- **documented** — this skill or a `CLAUDE.md`, for what the repo cannot change
  and no check can hold (a platform behaviour, a procedure);
- **tracked** — an issue with the evidence (run ids, pull request numbers, the
  failing output) and a proposed fix, never just the symptom.

A note with no signal — it has not bitten, will not, and costs nothing left
alone — is not a lesson, and is dropped (`CLAUDE.md`, *File an issue only on a
signal*).

**Mid-batch, fix what blocks or bites twice.** When a lesson costs the running
batch time — a gate that misleads, a brief that makes every agent re-solve the same
trap — fix it now. It is infrastructure, so it outranks whatever was next.
Correcting a stale description — a skill, a `CLAUDE.md`, a README — is part of
that and needs no one's approval; changing a **rule** is changing a decision,
which needs the user's approval, so it is filed with `planning` and raised at the
next check-in (`CLAUDE.md`, *Issues*, the stage labels).

**Otherwise, file it and keep going.** File an agent's "follow-up, not in this
pull request" notes and a pull request's open decisions the moment you read them,
not at the end — each one that carries a signal; the rest are dropped. Every
issue you file on your own carries `agent`.

**At the end, run a retro before reporting back:**

1. List every trap, gap, surprise, workaround and hand-back from the batch: your
   own notes, each pull request's decisions, the issues the agents filed. Ask the
   question the user would otherwise have to: what would have made this batch
   faster, or less work? Each answer is a lesson like the rest.
2. Map each one to fixed, enforced, documented or tracked. Anything unmapped
   that carries a signal gets an issue now.
3. **Refresh the unstarted issues whose ground moved.** Add a short *Context
   update* comment to the issues next in line: what merged that they build on, and
   what changed under them. Re-scope or close any the batch made moot. Never touch
   a `planning` issue's scope.
4. Put the mapping in the report, so the user sees each lesson turned into a change
   rather than only described.

## Reporting back

The user is not reading the transcript of a batch. They take long — often hours,
usually overnight — and the transcript is, if anything, notes for Claude itself.

**The report opens with what is left for the user to do.** `make checks
SINCE=<when the batch started>` prints every human check still unticked in what
merged, ready to paste, then the open issues carrying both `planning` and
`human`, put to the user as a question: which label stays.

**When things go well, say what the result was.** When things did not go as one
would expect, say what the surprise was. That does not necessarily mean things went
badly; we write it down because the more we can predict, the better we improve.
Include the retro's lesson → change mapping.

Two things still interrupt, because they are the ones the user would want to
overrule and overruling is only possible while the batch is still running: **a
change to the user's own files** outside the repo, and **a decision reversed** —
where the issue said one thing and the branch did another.
