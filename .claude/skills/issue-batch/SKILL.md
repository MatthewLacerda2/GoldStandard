# Working a batch of issues

The user rarely has one issue. An idea becomes several, and more appear as coding
starts. This is how a set of them gets worked without the batch costing more than
the work.

## The queue is not the bottleneck here — collision is

Measure before importing anyone's rule. In the template as it stands, `backend.yml`
and `frontend.yml` each finish in **about 35 seconds**, cold and with no caching:
a `docker compose up --wait postgres`, a `pip install`, a `bun install`, and
`make backend` / `make frontend`. A rebase-and-re-verify costs under a minute.
Re-measure once your own suite is real — `gh run list` prints it — because the
whole of this section is downstream of that number.

So there is nothing to pipeline around. In a compiled monorepo the merge queue is
the scarce resource and the shape of the work is dictated by it; here it is
cheaper than the conversation about it. **Cap the number of branches in flight on
file collision and on how many diffs a person will actually read**, not on the
queue.

What survives from the compiled-repo arithmetic is the part CI never paid for:
over shared files, N branches cost **N(N−1)/2 rebases**. That is git's bill, not
the runner's, and it is still real. A clean rebase is seconds; a colliding one is
a session.

## Merges serialize per layer, not globally

Both workflows are **path-filtered** — `backend.yml` on `backend/**`, `Makefile`
and itself; `frontend.yml` on `frontend/**`, `Makefile` and itself. Two branches
in different layers do not share a gate and cannot break each other's, so they
merge in either order, or at once, and a re-run buys nothing.

**Within one layer they do serialize**, for a narrower version of the reason a
compiled repo serializes everything:

- `bun run check` runs `tsc --noEmit` over the whole frontend. One branch changes
  an exported type, another adds a caller; each is green alone and red together.
- `pytest` imports the whole backend. A helper removed here and used there is the
  same failure in a different language.

So: **one branch at a time into `main` per layer**, the second rebased and
re-verified. Across layers, do not bother.

The exception cuts the other way, and it is the dangerous one. **Nothing checks
the contract *between* the layers.** `frontend/src/lib/schemas/items.ts` says in
its first line that it mirrors `backend/schemas/items.py`, and the mirroring is a
human promise — no generated client, no shared schema, and the path filters mean
the backend gate never even runs on a frontend-only change. Two branches that
split one API change between them will both be green and the app will be broken.
Keep an API change on one branch.

## The files where everything collides

The ones every feature appends to. Two branches landing in the same one at the
same time is the case to avoid:

- **`frontend/src/routeTree.gen.ts`** — generated by the TanStack Router plugin,
  rewritten by every new route. Two route branches conflict every time, and the
  resolution is to **regenerate, never to hand-merge**.
- **`frontend/src/i18n/locales/{en,pt,es}.json`** — every user-facing string lands
  in three files, so one feature touching copy touches all three.
- **`frontend/src/styles.css`** — the `@theme inline` block *is* the design
  system's allowlist. Every new token appends here.
- **`frontend/eslint.config.ts`** and **`frontend/eslint-rules/index.ts`** — every
  new house rule is a line in each.
- **`frontend/bun.lock`** — never hand-merge it. Take one side whole and re-run
  `bun install`.
- **`backend/api/endpoints.py`** — every new router is a line here, and whether it
  goes above or below the `get_current_user` dependency is a decision, not a merge
  accident.
- **`backend/models/__init__.py`** — every new model, twice: the import and
  `__all__`.
- **`backend/core/config.py` and `.env.example`** — every new setting, in both,
  and a merge that keeps one and drops the other fails at startup, not at lint.
- **`backend/tests/api/conftest.py`** — every shared fixture.
- **`backend/requirements.txt`** — trivial to resolve, but a conflict all the same.

**Before starting a second branch, ask whether it lands in any of these.** Three
branches in `repositories/`, `components/ui/` and a workflow file barely touch each
other. Two branches both adding a route, or both adding copy, collide by
construction.

**Migrations are not a serializer today, and will be.** `init_db()` is additive
`create_all` with no Alembic, so two branches each adding a table or a column
merge in any order. That is a property of this skeleton, stated as a deliberate
upgrade path in `README.md` — not of the stack. The day a downstream repo adds
Alembic, two branches each generating a revision collide on `down_revision`, and
this section is wrong until it is rewritten.

## Group the work before splitting it

**Split by responsibility, not by parallelism.** If a parent's sub-issues all land
in the same file, they are **one branch**, not one each.

Splitting an issue so several agents can run at once optimises the half that was
never scarce, and manufactures collisions: four sub-issues each adding a locale key
is four rebases and four reviews for one coherent change. Sub-issues are for work
that is genuinely separable *in the code*, not for work that is merely listable.

A `minor` issue is not a branch. It rides along in whichever pull request is
already standing in that file.

## One worktree per branch

`CLAUDE.md` already mandates it. The reason is in `backend/tests/conftest.py`: the
test database is named `test_gs_<sha1 of the worktree root>`, so every worktree
gets its own database against the one shared postgres, automatically.

Two branches taking turns in one checkout share that database — and because
`create_all` **adds and never drops**, its schema becomes the union of everything
either branch ever declared. A column one branch removed sits there, and the other
branch's next insert fails on a `NOT NULL` nobody wrote. Cheap to avoid,
expensive to diagnose.

Two things a worktree does *not* isolate:

- **The compose stack is a singleton.** It binds 5432, 8000 and 3000 on the host,
  so only one worktree can hold it. `CLAUDE.md` says not to start it to "check"
  something anyway — the gates are how you verify.
- **Anything under `~`.** Bun's and pip's caches are shared, which is fine, and is
  the reason parallel gate runs are cheap here.

A worktree costs `backend/.venv` and `frontend/node_modules` — hundreds of
megabytes, not the gigabytes a compiled target directory costs — so removing one is
hygiene rather than survival. **Remove it the moment its branch merges** anyway: a
stale worktree keeps a stale test database alive behind it.

## Starting

- Assign the user the moment work actually begins, and tell them. No assignee
  means free for grabs. **Unassign** if it turns out the issue was never started.
- Worktree off the latest `main`, branch `feat/…` or `fix/…`, pushed under the
  same name.
- Pull request titled `{issue_number}-{branch_name}`, description opening
  `Closes #{issue_number}`, then Context / Solution / Surface / Result.
- **Open it as a draft on the first push.** Draft is not decoration on unfinished
  work; it is how work survives a session that ends badly — the issue is the
  durable context, and a hand-back comment may never get written. Know what draft
  costs here: both workflows carry `if: ${{ !github.event.pull_request.draft }}`,
  so **a draft pull request runs no CI at all**. Marking it ready is the moment
  anything is checked, and the local gates are what you have until then.

## The path to merged

There is no separate merge skill in this repo. This is the whole of it.

1. **Green locally first.** `make backend` or `make frontend` for the layer you
   touched, `make check` before opening. This is the no-drift rule paying out: CI
   runs these exact targets, so a local green is a real prediction — unlike a repo
   where the runner is a different machine. Two ways it can still lie: CI runs
   `make backend PYTHON=python` on a clean 3.12 with `requirements.txt` installed
   fresh, and `bun install --frozen-lockfile`. A `.venv` or a `node_modules` that
   has drifted from its manifest is green on nothing.
2. `git fetch origin && git rebase origin/main`, then push with
   `--force-with-lease`.
3. **Mark it ready.** That is what starts CI.
4. **Wait for the runs that should exist — and work out which those are.** Read the
   diff against the path filters first. A branch touching only root Markdown or
   `.claude/**` matches neither workflow and gets **zero checks**, which on the
   pull request page is indistinguishable from "checks have not started". Absent
   and passing are different states; never write a wait loop that reads zero
   completed checks as success. `gh pr checks <n>` alongside
   `gh run list --branch <branch>` tells you whether a run exists at all.
5. **Nothing but you stops a red merge** — `main` carries no branch protection and
   no ruleset. `CLAUDE.md` is the gate: never merge without the user's say-so;
   once given, carry it through without pausing — commit, push, merge as soon as
   CI is green, or immediately if CI does not run. If CI fails, stop and report.
6. `gh pr merge`, then remove the worktree and delete the branch —
   `deleteBranchOnMerge` is off, so both are yours to do.

**A red ready pull request stays ready** and is fixed forward. Draft is for work
that is genuinely unfinished, blocked, or handed over.

**Expect conflicts where every feature appends** (the list above). Two authors both
being right is the common case, and the resolution is usually to keep both sides,
ordered deliberately. Mechanical resolutions — an import list, a locale key, a
`requirements.txt` line — are fine to do directly. Hand one back when resolving it
needs to know *why* the code is shaped as it is: a router whose auth dependency
matters, two prose paragraphs that need ordering, a token whose name is a decision.

## Re-read the board after every merge

A merge changes the graph. Whatever the merged issue blocked is fair game the
moment it lands — so the decision is one merge wide, not one batch wide.

Re-reading is not a licence to start everything. The ceiling is the collision list
above and the reviewer's attention, and an unblocked issue left unstarted is not
wasted capacity — it is a rebase not yet paid for. Priority (`architecture` →
`infrastructure` → `bug` → `foundation` → `feature`, `documentation` any time)
orders what gets **merged**, not what gets started.

**A stage label is the only absolute stop.** `planning` and `human` mean *not
yet*, and no amount of the issue looking ready overrides that. Everything else is
startable the moment it exists, including an issue filed a minute ago.

## Briefing a subagent

Point it at the root `CLAUDE.md`, then the layer contract it will live in —
`backend/CLAUDE.md` or `frontend/CLAUDE.md` — then the issue. Issues here are
written to be read cold. Beyond that:

- Name the **base commit** and what has landed recently that it must respect.
- Name the **siblings** and which files they are touching.
- Tell it which gate to run: the layer target while working, `make check` before
  the pull request goes ready.
- Tell it **not** to merge — merging belongs to the session running the batch.
- Tell it **not** to start `docker compose`, a dev server, or anything
  long-running. The stack is a singleton and the gates are the verification.
- **Scratch filenames must carry the issue number.** The scratchpad is shared
  between sibling agents, and a collision swaps one pull request's description for
  another's.

## Model, as a hint

Judgement work — design, implementation, triage — wants the strongest model. A
rebase, a locale-file conflict, a regenerated route tree does not. Most sessions on
a branch are the second kind. The line is not crisp, so err upwards: a
"mechanical" rebase that turns out to need two authors' reasoning reconciled was
never mechanical.

## When to hand back to the user

- ≈3 attempts at the same failure.
- **A decision that is genuinely theirs.** This repo's reader is a developer, so
  hand back the engineering call rather than a simplified version of it — name the
  options and what each costs. The ones that are always theirs: a change to a
  request or response shape, a route or token name people will type, a layer
  boundary, a lint rule, and anything that moves what the **template teaches** —
  an upgrade path taken early, a convention the downstream reader will inherit.
  Anything a `planning` label would have carried belongs here too.
- The mechanics, per `CLAUDE.md`: push what you have, leave the pull request
  **draft**, comment the bottleneck, tag the user, and stop. Do not thrash.

Working unattended, a question that only blocks *one* issue is a comment on that
issue and a move to the next — not a night spent idling. A question that blocks the
batch is a hand-back.

## Reporting back

The user is not reading the transcript of a batch. They take long — often hours,
usually overnight — and the transcript is, if anything, notes for Claude itself.

**When things go well, say what the result was.** When things did not go as one
would expect, say what the surprise was. That does not necessarily mean things went
badly; we write it down because the more we can predict, the better we improve.

Two things still interrupt, because they are the ones the user would want to
overrule and overruling is only possible while the batch is still running: **a
change to the user's own files** outside the repo, and **a decision reversed** —
where the issue said one thing and the branch did another.
